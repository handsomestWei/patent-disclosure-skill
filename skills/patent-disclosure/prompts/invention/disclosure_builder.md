# 技术交底书生成模板（Step 7 · 发明）

**本文件仅用于发明。** 实用新型 / 外观见 `../utility_model|design/disclosure_builder.md`（**勿**用本章 3.2/3.4 mermaid 系统主线去写结构或外观案件）。

详细章节范例与 **mermaid** 图示模版见同目录 **`template_reference.md`**。

## 7.1 章节结构

```
1. 注意事项
2. 一、介绍相关技术背景，描述与本发明技术最相近的现有技术，并说明该现有技术存在的缺点
   - 1.1 现有技术（按技术方向分类，含专利检索结果；过 / 带疑点过须点名最接近的一篇 + 逐特征表，**不过**见 **§7.10** 降级）
   - 1.2 现有技术存在的缺点（过 / 带疑点过落到 D1 或 D2；**不过**落到材料/常规做法，见 **§7.10**）
3. 二、针对上述缺点，说明本发明所要解决的技术问题（由 Fk 的技术效果反推，**不得**写入本发明手段；正文写完整问题句，见 **§7.10**）
4. 三、本发明技术方案的详细阐述
   - 3.1 背景（场景与参与者、标题对象如何进入系统、后文高频术语的场景定义；细则 **§7.9**）
   - 3.2 系统框图（**mermaid**，如 `flowchart` + `subgraph` 分层；交付前经工具转 PNG；**不要** ASCII 文字框图）
   - 3.3 模块功能说明（聚焦作用与关联关系，非输入输出）
   - 3.4 系统流程说明（**mermaid 流程图**，交付前经工具转 PNG；**不要** ASCII 文字/箭头流程图）
   - 3.4.1 符号与公式（出现公式或形式化变量时**须设**；**先**写案件目录 `formula_plan.yaml` 再成文；材料式保真，见 **§7.7**、**`template_reference.md` §3.4.1**）
   - 3.5 关键技术参数（参数表「符号」列与 3.4.1 **同形**）
5. 四、与现有技术相比，本发明具有哪些优点？（完整效果句，构造写进句子里；F 号最多句末括注，见 **§7.10**）
6. 五、本发明的技术关键点和欲保护点是什么？（**5.1 必要技术特征 / 5.2 优选特征**，按删除测试划分，见 **§7.10**）
7. 六、其它（实施例、技术效果、参数示例）
```

**第一章 1.1 撰写硬性要求**：在「按技术方向分类」的**每一条**现有技术（专利或文献）末尾或表格中，必须给出 **经核验的公开源 URL**（规范与示例见 `prior_art_search.md` 与 `template_reference.md` §1.1）。第二轮不足 4 条时按 `prior_art_search.md` **3b** 从第一轮同分类号回补，仍少如实写近邻较少，**禁止编造条目凑数**。**国知局检索**（`EPUB_HITS_JSON`）中对该专利给出的 **`abstract` 非空时**：文中「技术方案 / 应用 / 局限」类表述**须以摘要理解为前提**（消化后重写，非整段粘贴），**禁止**与摘要明显矛盾或脱离摘要杜撰；详见 **`prior_art_search.md`**「`abstract` 必用」。

**禁止输出**：交底书正文中**不得**包含「自检清单」章节，例如检查项表格或带状态符号的清单列。自检见 `disclosure_self_check.md`，**内部执行**，不写入交付正文。

**禁止仓库/技能脚注**：交付用 Markdown **末尾不得**出现任何指向本技能或示例仓库的说明，例如「本文件为 `patent-disclosure-skill` 仓库内教学示例」「不构成任何法律或技术承诺」「虚构教学」「详见 `examples/`」等。正文**止于第六章及此前章节**；**不要**在文末追加斜体免责或仓库署名。

## 7.2 文档头部模板

```markdown
# 技术交底书

**案件名称**：[待填写]一种XXX方法及系统

**技术联系人**：
- 姓名：[待填写]
- 电话：[待填写]
- 邮箱：[待填写]

**专利类型**：发明

---

## 注意事项

（1）交底书应使代理人能看懂，尤其是背景技术和详细技术方案，一定要写得全面、清楚、完整；
（2）技术的公开程度，应以本领域普通技术人员不需付出创造性劳动即可进行实施为准。
（3）在与代理人沟通时，对于代理人咨询的技术问题，应给予回答并认真讲解，并且按要求及时正确地补充相应技术材料。
```

## 7.3 输出文件命名（用户产出目录，必遵循）

在用户目录（如 `outputs/{案件标识}/`）写入交底书 **Markdown / Word** 时，**主文件名须体现正文中的「案件名称」**，且**凡向用户落盘交付的定稿均须带时间戳后缀**（见下第 5 点），避免无区分度的固定名（如一律 `disclosure_draft.md`）。**仓库内 `examples/` 为教学统一可仍用固定名**；用户产出不适用该惯例。

1. **提取**：从 `**案件名称**：` 行取完整发明名称；去掉占位（如 `[待填写]`、`【待填写】`）、首尾空格。
2. **规范化**：删除或替换 Windows 非法字符 `\ / : * ? " < > |` 与换行；连续空格可压为单个空格或删去（中文标题通常无空格亦可）。
3. **长度**：文件名（不含扩展名）建议 **≤ 80 个字符**；超长则**截断**到约 80 字并保留语义完整（例如截在「方法及系统」等结尾词之前），勿用无意义随机串。
4. **定稿命令**：`mermaid_render.py` 的 `-o` / `--docx` 须使用**同一主文件名**，且该主名**必须符合第 5 点**（**案件名 + `_` + 14 位时间戳**）。示例（案件名已按上文规范化、过长已截断时）：

   `python tools/mermaid_render.py -i "…草稿.md" -o "一种异构计算环境下基于资源画像与限频重排队的批任务调度方法及系统_20260408143025.md"`

   默认同目录生成同名 `.docx`。过程性中间稿（仅自用、非交付）文件名可自定，但**最终交付**不得省略时间戳。

5. **时间戳后缀（凡落盘交付必遵循）**：凡写入用户产出目录、作为**向用户交付**的技术交底书 **`.md` / `.docx`**，主文件名须为：  
   **`{§7.3 规范化案件名}_{YYYYMMDDHHmmss}.md`** 与同名 **`.docx`**。  
   - **首次定稿**与**迭代合并/纠正**适用**同一规则**；每次交付取**当次落盘时**的**本地时间** 14 位数字（年月日时分秒各 2 位，如 `20260408143025`）。  
   - **不要覆盖**已有交付文件；新一次交付即**新时间戳**、新文件名。用户**明确要求**覆盖某路径时从其意。  
   - **`mermaid_render.py`** 的 `-o` 与可选 `--docx` 须与上述主名一致。  
   - **例外**：（1）仓库内 **`examples/`** 示例可继续固定文件名；（2）用户书面指定文件名时从其意（仍建议保留时间戳以免混淆）。

Agent **落盘时**即采用上述命名，并在回复中写明路径，便于用户对照标题与磁盘文件。

## 7.4 系统框图与流程图要点

- **系统框图与流程图**均仅用 **fenced mermaid**（`mermaid_render.py` 经 Playwright 出 PNG，不依赖 Node/mmdc 或外网 PlantUML）；Word 中以 PNG 为准，**无需**再附 ASCII 文字框图
- mermaid 内节点标签用**场景短词**（中文/数字），避免 ①②③；**用标题里的领域对象**，不要换成更空的上位词。可另写简短「流程说明」段落概括各步，**不得**用 ASCII 框线箭头代替图示。实现细节（校验值、序号、租约字段等）放正文，不要堆进节点标签。
- **生图**：出图后端不是 `local` 时，先按 `prompts/figure_generation.md` 对草稿跑 `figure_jobs.py prepare --from-md`，逐块出图、读图 QA、`record`。定稿时 `mermaid_render.py` 加 `--ai-figures outputs/{案件标识}/figure_jobs.json`：已登记的块用生成图，其余照旧本地渲染。mermaid 围栏仍是结构规格，**照写不省**。
- **步骤号必须写进可见标签**。节点 id（`S1`）**不会**出现在 PNG 上。正确：`S1["S1 采集节点指标"]`、`S5{"S5 是否达阈"}`。错误：`S1[采集节点指标]`（出图只剩中文、序号丢失）。定稿时 `mermaid_render.py` 会把缺失序号补进标签再出图；成文时仍须按正确写法写，勿依赖脚本补救。

### 用户点名的场景 / 示意图

仅当用户指定路径或说「这张图是场景示意，补充到交底书」：

1. **`Read`** 该图，判别种类（见 `project_scan.md`「图片与裸图目录」）。
2. 图标、切图、营销场景：**不入文**，对话说明原因。
3. 技术示意图 / 拓扑 / 对照图：拷到案件 `assets/`，在 3.1 或第六章用 `![…](assets/…)` 嵌入，写「如图 N」，给图题。不要改画，不要扫描其他素材目录。
4. 框图和流程仍用 mermaid；点名图是**额外**附图，不替代 3.2 / 3.4。

## 7.5 脱敏要求

| 类型 | 脱敏方式 | 示例 |
|------|----------|------|
| 业务/行业 | 抽象为通用描述 | 「XX检测」→「多标签分类场景」 |
| 具体分类 | 用 ABC 等替代 | 「类别1、类别2」→「分类A、分类B、分类C」 |
| 具体数值 | 用范围或示例说明 | 「每日 N 人」→「每日一定规模」 |
| 公司/产品 | 不出现具体名称 | 删除或替换为「某系统」 |

**脱敏边界（勿误抽）**：上表挡住的是真实主体、产品名、内部代号和不宜公开的精确数值。  
**不得**借脱敏把**案件名称中的领域对象**收成更空的上位词（标题有「数字员工」则正文/框图用该对象，勿改成「岗位集群」；标题有「资源画像」则勿改成「节点数据」）。实施例中的角色名、工具类别、交付物类型从本案材料归纳，**要具体**，只去掉公司名与真实数据。术语与标题贯穿见 **§7.9**。

## 7.7 符号与公式体例（必遵）

撰写 **3.4.1**、**3.5** 及全文含 LaTeX 的段落时须遵循；正/反例见 **`template_reference.md` §3.4.1**。  
合同：`references/schemas/formula_plan.schema.yaml`。范式库 **`references/formulas/paradigms.yaml`** 只给 **材料没有的式** 当起草菜单（说明见同目录 `README.md`）。

### 成文前：`formula_plan`（有公式时必做）

1. **先扫材料**：扫描根内有 `.tex` 时：案件目录已有 **`tex_formula_inventory.md`** 则 **只 Read 该清单** 勾选，不必把 `.tex` 再载入成文上下文；无清单则按 **`prompts/tex_scan.md`** 补做。公式优先从源码/清单勾选。编号公式、Word 正文中的式、PDF 插式一律列入候选（出处 + 一句话在算什么）。对照 **已选专利点 / 3.3 / 3.4** 勾选进 `equations`；不采用的写入 `omitted`（`ref` + `reason`），禁止静默丢掉。  
2. 在案件目录写出 **`formula_plan.yaml`**：每条式标记 **`origin: source`（材料转录）或 `origin: agent`（技能补写）**。source 填 `source_ref`、`source_kind`（`tex` / `md` / `word_text` / `pdf_text` / `other`）与原文 `latex`；只做分隔符等机械体例时把原材料写入 `original_latex`。材料式是否改写，见公式正/反例表「选题」行。  
   - 有 `.tex` 链则 `source_kind: tex`（默认已核）。  
   - 仅从 `pdf_to_md` 文本层抄的式子：`source_kind: pdf_text`，`verified: false`。  
   - **`verified: false` 的式子可写进 3.4.1 转述，不得当作 Fk / 创造性依据**；不因此停笔、不问用户补源码。  
3. **仅当材料没有对应式** 才 `Read` `references/formulas/paradigms.yaml`（或 `python tools/formula_paradigms.py list [--case-dir …]`），为 agent 式选 `paradigm_id` / 可选 `combo_id`，并给 **可代入数值例**。  
4. 校验：`python tools/check_formula_plan.py -i …/formula_plan.yaml --eval`；**不通过不得写 3.4.1**。简单 agent 式由脚本代入 `numeric_example`；source 复杂式脚本会跳过，须手算或从缺，**不得**为通过 `--eval` 降维改写。  
5. 再写正文 3.4.1：只展开计划中的式。agent 起草的打分与限频触发宜分式 (1)/(2)。  
6. 建议顺序：**流程文字 → 从材料锁定公式 →（缺口才起草）→ 回填符号表 / 3.5**。

覆盖范式（仅 agent）：环境变量 `PATENT_FORMULA_PARADIGMS`，或案件目录 `formula_paradigms.yaml`。

### 符号、上下标与分隔符

撰写 **3.4.1** 前先写符号表：每项含符号、含义、下标含义、量纲或取值范围。其后公式、3.5、实施例与符号表同形同义。上下标、分隔符、防零除、同一字母、材料式是否改写，以 **`template_reference.md` 公式正/反例表**为准。

出 Word 只用当次时间戳定稿 md。分隔符改正后重跑 `mermaid_render.py` / `md_to_docx.py`。`LATEX_DELIM: hits=` 大于 0 时，先改成 `\(...\)` 再对已写出的时间戳 md 重跑。定稿前可跑 `python tools/latex_delimiters.py -i <定稿.md>`。

### 跨节一致

- **3.4.1 符号表**、正文首次定义式、**3.5「符号」列**、**第六章实施例** 四处须 **逐字同形**。
- 修改任一处符号时，须同步核对上述各处及 3.3/3.4 文字叙述中的同名变量，并更新 **`formula_plan.yaml`**。

`python tools/mermaid_render.py -i <含图示的草稿.md> -o "<案件名_YYYYMMDDHHmmss>.md"`（默认在同目录生成**同名** `.docx`；可用 `--docx` 指定路径，`--no-docx` 跳过 Word。出图后端不是 `local` 时加 `--ai-figures outputs/{案件标识}/figure_jobs.json`，见 §7.4「生图」。Word 失败时见终端提示的手动命令。默认不预渲染公式 PNG，不安装 matplotlib。）

（mermaid 出图：Playwright + 内置 `tools/vendor/mermaid.min.js`，与查新共用浏览器，见 `tools/browser.py`。`--probe` 显示本机无 Chrome/Edge 且无自带 Chromium 时，才允许一次 `playwright install chromium`。无可用浏览器时仍交付 .md；Word 可生成但框图可能为代码块，告知用户补浏览器后可重跑本脚本。）

**判读（stderr ≠ 失败）**：以 **退出码 0** 和机读前缀为准：`MERMAID: ok=`、`DOCX: ok=1`、`MATH:`、`omml_text_fallback=`、`LATEX_DELIM:`。PowerShell 红字 / `NativeCommandError` / 中文乱码不算失败。`DOCX: ok=0` 才按终端里的手动 `md_to_docx.py` 命令补做。`LATEX_DELIM: hits=` 大于 0 或 `DOCX: ok=0 reason=latex_delim`：Word 未生成，把行内公式改成 `\(...\)` 后对**已写出的时间戳 md**重跑。

### OMML 失败后的公式 PNG（可选，默认关）

Word 公式主路径为 `latex2mathml` → 可编辑 OMML；失败则 **留 LaTeX 原文**。定稿默认不预渲染公式 PNG。

若 stderr 出现 `omml_text_fallback=` 或 `OMML_FAIL:` 或 `MATH: ... text=`（`text`>0）：

1. **先完成交付**（仍须写明 `.md` / `.docx` 路径）。
2. 在 **`## 交付后请确认`** 第 1 条以 **`(a)` 标签**反问 **一次**（请回 **是** / **否**），列出失败公式摘要；说明须额外安装 matplotlib（约 100MB，含 numpy 等），图片在 Word 中不可再编辑。若同轮 STEP 也待问，按 `prompts/delivery_confirm.md`「同一轮至多一个是/否」**只问本条**，STEP 改为陈述。细则同该文件。
3. 未得 **是**（含未回复）：保持当前 docx，不安装 matplotlib。
4. 用户回 **是**：本会话最多一次 `pip install matplotlib`（已装则跳过），再对**同一份已定稿 md** 覆盖同名 Word（不必重跑 mermaid）：

   `python tools/md_to_docx.py -i "<同名.md>" -o "<同名.docx>" --base-dir "<md 所在目录>" --math-render`

   仍走 OMML 优先；PNG 也画不出的保持原文，**不要再问第二轮**。

脚本禁止 `input()`；反问只在对话里进行。全成功则不问。

## 7.6 交付回复：交付后请确认（必做）

每次向用户**交付**定稿（已写明 **`{案件名}_{YYYYMMDDHHmmss}.md` / `.docx` 路径**）时，在同一条回复**最后**按 **`prompts/delivery_confirm.md`** 输出独立小节，标题固定为 **`## 交付后请确认`**。不得写入交底书正文。

偏向点、围栏一句、政策简报、STEP/公式 PNG 反问都进该节对应条目，不要再另起散文段。第五章侧重规则仍须遵守：对举来自本稿，**禁止捏造**。

**合并 / 纠正迭代**再交付定稿时仍须有该节（围栏第 3 条默认省略；政策简报按 `soft_nudge.md` 抑制条件）。

## 7.8 交付回复：STEP 解析（可选，默认关）

## 7.9 场景术语、标题贯穿与实施例（发明成文必遵）

代理人须能对着本案场景读懂第三章。细则与正/反例见 **`template_reference.md` §3.1 / §3.2 / 实施例 / 第五章**。

### 术语：贴合话题背景（默认就用领域词）

首次成文即用**本案标题与 3.1 场景里能读懂的词**，不要等用户指出后再换。

- **框图 / 步骤标签**：场景短词，且属于本专利话题（教学、岗位协同、家庭回忆等以标题为准）。
- **3.1 及后文**：核心对象和高频过程都用领域可读名。需要把判定方式写清时，用双层：**领域名（如何判定/如何记录）**，括号里也用白话机制，不要把另一领域的行话当正式名称。例：「实际使用资料清单（按实际读过的资料名称与版本登记）」。
- **话题错位检测**：若某词放进标题/3.1 场景会显得像在写分布式协议、内容寻址或账本系统，而本案并不是该领域，则**整篇换成领域表述**，不要靠 3.1 定义把错位词留下来。指纹、水位、证据账本、幂等标识、媒体锚点、事件证据库等只是**错位词的例子**（随案件而变），**不要**做成禁词表，也**不要**因为「先定义了」就保留。
- **机制仍在**：换成领域词后，仍须能实施（如何区分已用资料、如何跟变更对齐、如何避免重复执行等）。禁止只换词却说不清判定；也禁止为了保留机制而继续用错位行话当正文术语。
- **何时可用实现词**：该词本身就是本案话题（例如发明就是内容校验或水位协议）时，在 3.1 定义后使用。判定标准是**是否属于本标题的领域**，不是「技术上是否精确」。
- **禁止**把某一案件的配置机制（例如「岗位技能包」）写成所有标题的必写模块。

### 3.1 须铺对象与术语（三小段，不另开章）

1. **场景与参与者**：用案件名称里的领域对象称呼执行主体，不要只用「系统/模块/岗位」代替。
2. **标题对象如何进入系统**：从**本案材料**归纳该对象如何被配置、调度或进入执行（有则写清职责边界、资料/工具范围、交付与转交；材料没有则不要编造固定机制）。
3. **高频术语各一句场景定义**：后文将反复出现的**领域词**在 3.1 立住并全文同词。不要为错位行话做定义来「合法化」它。

### 3.3 / 3.4 结构

- **3.3**：按 3.2 框图节点写成**独立模块**（一项一个模块，写清作用与关联），不要把多个节点揉进一条。
- **3.4 正文**：按图中步骤号 **逐项对应 S1—Sn**，与 mermaid 一一对应；不要几步合成一段且不点序号。

### 标题关键词贯穿框图、流程、实施例

从案件名称取出领域实词（可忽略「一种」「基于」「方法及系统」等套话）。这些实词须：

- 在 **3.2 框图**中作为节点或执行主体出现，**不得**换成更空的上位词；
- 在 **3.4 流程**中做事（步骤名或步骤说明里出现），不能只在 3.1 出现一次；
- 在 **第六章**以 **2～3 个有名字的实例**走完主路径，名称与 3.1 / 3.2 相同。

### 实施例：角色齐、路径齐

- 实例须带：职责、可调用能力（工具/资料范围）、交付物、相互依赖；不要只列岗位或模块名。
- 至少覆盖 **主路径 + 一条与本案相关的分支**（如变更影响、中断接管、冲突裁决、限频重排等，以第三章已有分支为准）。
- 实施例是把标题对象走成可想象的业务故事，不是 3.4 的缩写复述。

### 第五章不写虚

- 保护点**可以**跟 3.1 的场景词。
- 每条独立点仍须是**可实施机制**（输入、判定、控制或输出如何做），禁止写成「有三个××」或仅罗列角色名称。
- 用户要求换术语时视为**术语族替换**（见 `merger.md` / `correction_handler.md`）：1.1、第二章、3.1–3.5、第四–六章及 mermaid 标签一并替换，禁止只改 3.3 一句。

## 7.10 创造性主线：D1 与区别特征 Fk（发明成文必遵）

Step 5 已按 `prior_art_search.md`「D1 锁定与区别特征 Fk」落下 **`查新与区别定位_*.md`**（含门禁三态与证据级别）。审查骨架是 **口径唯一**（同一 Fk = 同一构造/机制），不是把 F1、F2 当成全文主语。

内部定位稿用 D1/Fk 编号。交底正文要让发明人顺着读完、代理人仍能对上审查框架，**不必**把「唯一 D1」写成仪式性套话。过 / 带疑点过：点名最接近的一篇、给出选定理由、用技术维度对比即可，标签写「最接近的现有技术（D1）」。**不过**：见本节「降级成文」，**禁止**假 D1。

`formula_plan` 里 **`verified: false`**（含默认的 `pdf_text`）的材料式**不得**单独当作 Fk。不因此中断成文。

### Fk 出场（正文可读性，硬项）

**定义一次**：1.1 比对表用「编号」列；「本案怎么做」写满构造。表后 **特征一览**（每条：`F1 中文简称：一句话构造`）。后文只用这些简称。表式见 `prior_art_search.md` 与 `template_reference.md` §1.1。

**禁止**：最后一列「是（F1）」；把列名叫「本专利权要」；后文只写 F1 逼读者回头翻表。

| 位置 | 怎么写 |
|------|--------|
| `查新与区别定位_*.md` | 可密写 Fk |
| 1.1 表 + 特征一览 | **唯一定义处** |
| 1.2、二、四 | 完整中文句；F 号最多句末括注一次。禁止「对应 F1：」「由 F1 带来：」当条目标题或句首 |
| 三、六 | **禁止 Fk**；发明用模块/步骤号，实用新型用件号 1–6 |
| 5.1 | Fk 作条目标签，**每条复述特征全文**（离开编号仍可读） |

自检看的是「口径同一、离开编号仍可读」，不是「是否每段都出现 Fk」。

### 第一章：主比对钉一篇，允许 D2 补行

- **过 / 带疑点过**：1.1 在按技术方向列举之后，**点名最接近的一篇**：公开号 + 标题 + **一句选定理由**，随后给**逐特征比对表**（3～5 行，维度为技术维度；编号单独成列，见上「Fk 出场」）。其余检索条目作技术背景，**不要**五篇并列逐特征。
- **D2 补行**：仅当 D1 未覆盖、本案有、且 D2 可能被拿来组合时，在主表下加行并标明 D2；不是第二套出发点。「本案怎么做」用中文写联用的构造，不要只写「与 F1、F3 联用」。
- 门禁为 **带疑点过** 时：选定理由后加**一句**证据边界（如「依据公布摘要，公开文本未通读」或「两篇接近，本篇作出发点、某某为 D2」），**禁止**写成已核实全文对比。
- 过 / 带疑点过：1.2 每条缺点须能落到 **D1 或 D2 一侧的具体不足**上，写成完整句子（句末可括注 F1）。**禁止**「对应 F1：」当条目标题。**禁止**只写「现有技术普遍存在不足」。

### 第一章补则：门禁「不过」时降级成文

**仍写交底**，创造性骨架降级，不是停笔。

- 1.1 **不**点名最接近的一篇；检索命中（含远领域噪声）只作背景，**禁止**把不相干专利标成 D1，**禁止**编造公开号或链接。
- 写明「本次检索未钉住可作最接近现有技术的对比文件」。区别对**材料里的现有做法 / 本领域常规**写，Fk 仍在 1.1 一览与 5.1 编号，标明未经对比文件钉死；1.2 / 二 / 四仍说人话。
- 1.2 指到上述现有做法的具体不足，**禁止**「本质区别」「创新性强」等无指向套话。
- 该拆案时 5.1 写明无共同必要特征，不要为了凑一条 D1 把两组发明点捏成假对比。

### 第二章：三段绑定（技术问题由技术效果反推）

每条站得住的 Fk 都要能填出三段：**Fk → 该特征在本方案中的技术效果 → 实际解决的技术问题**。这三段写在定位稿或成文推理里。**第二章正文只写第三段的完整问题句**，不要写「（对应 F2）」或把 F2 当小标题。

**硬项**：技术问题的表述里**不得出现该特征的手段词**，也不得包含对该手段的指引或暗示。技术问题说的是「要达到什么」，**不是**「怎么做」——把手段写进技术问题，等于把答案抄进题目，审查侧极易据此认定显而易见。

```text
（坏）本发明要解决的问题是：现有调度未将任务需求与节点多维资源画像联合用于二次排序，
      因此需要一种基于资源画像与限频重排队的调度方法。
      —— 「资源画像」「限频重排队」是本案手段，不能出现在技术问题里

（坏）如何在不引起调度震荡的前提下降低长尾任务等待时长。（对应 F2）
      —— 问题句合格，但「对应 F2」造成阅读跳转，第二章不要这样写

（好）F2（间隔阈值与分数变化阈值双条件触发重排）
      → 技术效果：分钟级刷新下不引入反复重排造成的调度震荡，同时缩短长尾任务等待
      → 技术问题：如何在不引起调度震荡的前提下降低长尾任务的等待时长
      —— 只说要达到的效果，不出现「限频」「重排」「画像」等手段词
      —— 第二章只保留最后一句完整问题
```

多条 Fk 在**功能上相互支持、共同**产生一个效果时（如 F1 给出分数、F2 用分数变化做触发），**按整体写一条问题**，不要拆成互不相干的三条——拆开后每条单独看都容易显得显而易见。F 号映射放在 1.1 一览和 5.1，不放在问题句后。

### 第四章：优点写完整效果句

- 每条优点用**完整中文句**写出效果，并把带来该效果的构造/机制写进句子（发明人离开 F 号也能读懂）。句末可括注（F1）。
- **禁止**「由 F1 带来：」当句首或条目标题；**禁止**只写「提升效率」「增强鲁棒性」而不写是哪段构造带来的。
- 存在协同关系时，用一段整体论述说明单独任一构造都达不到该组合效果（不要写成「F1、F2、F3 的协同：」运算式）。

```text
（坏）由 F1 带来：压紧力经支撑柱传到基板……相对 D1……
（好）压紧力经两侧支撑柱传到基板承力区，导热压板与芯片保持贴合，焊点与走线密集区少受持续载荷；相对螺钉穿散热器调节，板面零件更少。（F1）
```

### 第五章：必要 vs 附加（删除测试）

**删除测试**——把某条特征从独立保护构思里删掉，方案**还能不能解决第二章的技术问题**？

| 结果 | 归属 | 放哪 |
|------|------|------|
| 不能解决 | **必要技术特征** | **5.1 独立保护构思** |
| 仍能解决 | **附加 / 优选特征** | **5.2 优选特征** |

- **5.1** 每条写「特征描述 + 对应 3.x / Sx / Mx / 式 (n)」，编号与 Step 5 的 Fk **相同**；条目数宜等于站得住的 Fk 数；**复述全文**，不要只写 F1。
- **5.1 不写**「根据权利要求 1…」这类正式权项句式（交底书不是权利要求书；书式取向留给 `## 交付后请确认` 第 2 条），也**不写**「有三个××」（见 **§7.9**「第五章不写虚」）。
- **5.2** 放阈值取值、窗口长度、可选分支、独立子主题等；只剩参数取值差异的 Fk 归此处，**不要**硬写成独立创新点。
- 若出现 **≥2 组彼此没有共同必要特征**的发明点，在 5.1 写明**总的发明构思**，或按 `patent_points_analyzer.md` 建议拆案，不要混成一篇的并列独立点。

**实用新型**同样适用本节主线，比对维度换成部件与连接关系，书式仍按 `../utility_model/disclosure_builder.md`。能指到具体文献时优先 **带疑点过**；指不到则 **不过** 仍成文、降级写，禁止假 D1。**外观设计不适用**本节，按 `../design/disclosure_builder.md` 写与在先设计的造型/图案/色彩差异。
