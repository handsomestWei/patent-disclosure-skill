# 申请文件 · 说明书与摘要

交底提供技术方案事实与可实施方案。按申请书式写五部分。附图已按 `figures.md` 画出后再写「附图说明」，嵌入 `figures/图N.png`。

材料出处见 `references/disclosure_to_spec_map.md`。从属层与「第一种/第二种」实施例对齐，见 `claim_strategy.md`。

发明分案先按 `divisional.md` 核实原始申请，并在「技术领域」前写原申请说明段落。

## 五部分

| 部分 | 写法 |
|------|------|
| 技术领域 | 一句：本发明涉及…，属于…技术领域。 |
| 背景技术 | 交底第一章消化成叙述，不是检索列表。优先 **1 件**最近对比写透；确有另一类独立现有技术再加第 2 件。禁止检索说明、分组综述、来源 URL、数据库名、「经检索」。结尾可加背景信息未必构成现有技术。 |
| 发明内容 | 针对上述问题 → 独立方案（与独权步骤一…同序）→ 必要从属要点按从属树「进一步」简述 → **有益效果**单独成段，效果须能对上手段。系统方案用模块名。 |
| 附图说明 | 「图1为…示意图；图2为…示意图。」点名场景图同样列「图N为…示意图」。框图不列（10）释义。插图用 `![图N](figures/图N.png)` |
| 具体实施方式 | 结合附图把主方案按步骤一…走通。`claim_tree` 里 `aligns_embodiment: 第一种` 的从属在第一种实施例展开；`第二种` 对应分支。公式、符号、数值例、交底已有表格写在这里。交底没有的硬件细节不要编。 |

### 背景技术（叙述，不要检索列表）

Markdown 里不要手写 `[0002]` 段号（客户端/排版会加）。结构按公布稿习惯：

1. **点名 1 件最近对比**（交底第一章里与本发明场景、手段最接近的那件）：`中国专利申请（公布号：CNxxxxxxxxA）公开了……` 用一段写清它实际做了什么，不要只丢标题。
2. **针对本发明缺什么**：另起一段或两段，用「上述方案……但没有公开如何…… / 无法用于……」。缺口必须对上交底第二章的技术问题，不要空泛「效率不高」。
3. **可选：不带号的常规做法**（交底 1.2 里的行业惯用手段，如静态优先级、事后迁移、遥操作）。写它做了什么、为何仍解决不了本问题。没有第二类手段就不要硬凑。
4. **收束**：`本背景技术中公开的信息仅用于理解本发明构思的背景，因此它可以包括不构成现有技术的信息。`

不要连续罗列三件公布号各写两句。第二件对比仅当与第一件手段明显不同（例如一件是分片派发、另一件是画像匹配）时才写，写法同第 1–2 步。

**正例（结构，勿抄领域）：**

> 中国专利申请（公布号：CN112506632A）公开了一种分布式系统中批任务的调度方法和系统，由任务调度器根据应用服务器在线情况确定分片总数，为在线服务器分配分片编号，服务器按编号批量拉取任务并以流方式处理，用以避免任务冲突。
>
> 上述方案主要用于按节点是否在线及分片编号进行批任务分发，但没有公开如何在派发前把任务需求向量与节点多维资源画像合成为匹配分，也没有公开仅在时间间隔与窗口分数变化同时达阈时对队首窗口重排，难以纠正静态优先级造成的资源错配。
>
> 进一步，现有调度还常在超阈值后再迁移任务。该做法能够在过载后调整，但无法在派发前按实时余量排序，指标抖动时也容易对全队列反复重排。
>
> 本背景技术中公开的信息仅用于理解本发明构思的背景，因此它可以包括不构成现有技术的信息。

**反例：** 在某数据库以关键词检索得到 CN1×××、CN2×××、CN3×××，该专利公开了……（检索腔，删除）。连续「中国专利申请CNxxxxA公开了……该方案未……」排三件，像查新摘录，同样不要。

实用新型用「本实用新型」。正式说明书不要写问题清单。

## 表格

表格不是法定必需要件。交底里**已有**多行同结构数据（参数清单、对照实验、配置/覆盖对照等）时，说明书**必须保留表形态**，不得收成「本实施例中可取…」一段。

- 正文先点题（如「具体校验结果见表1」），再写 Markdown 表；表题用「表1」「表2」，按实施例出现顺序编号
- 表放说明书正文，**不**当附图、**不**进权要
- 实施例取值在表下加一句：上述数值仅为实施例，不作为权利要求限制
- 交底只有一两处零散数字：用「本实施例中」叙述，不要为了像公布稿而造表
- 交底没有的行、列、实验结论不要编；有表漏搬则记问题清单

## 公式

交底目录有 `formula_plan.yaml` 则 **`Read`** 后写入具体实施方式：先符号表，再只展开计划中的式，数值例与计划 `numeric_example` 或表 N 一致。权要只保留文字关系。计划没有的主式不要编。

## 摘要（`说明书摘要.md`）

- 结构：技术领域一句 + 现有不足一句 + 手段（与独权同序的要点）+ 效果一句。不要背景展开、不要权利要求编号、不要宣传语（词库 `references/promo_terms.yaml`）。
- 文字部分一般**不超过 300 字**（汉字与字母数字合计，不含图）。超了先删背景与效果形容词。
- 摘要附图：`figures/摘要附图.png`，默认主流程图，与 `suggested_abstract_figure` 一致。

## Word

```bash
python skills/patent-application/tools/emit_application_docx.py --dir <产出目录>
```

公式尽量 OMML；失败记问题清单，仍出 Word。

**行内公式必须写 `\(…\)`**（或全文统一 `$…$`），**禁止**用普通括号包 LaTeX（`(M_{\mathrm{total}})` 在 Word 里是纯文本，常带拼写红线）。Markdown 预览把 `\(` 显示成 `(`，勿据此删反斜杠。`emit_application_docx.py` 遇命中会对该文件打印 **`DOCX: ok=0 reason=latex_delim`** 并**跳过写出**；须改分隔符后再重跑。定稿前可单独跑：

```bash
python skills/patent-application/tools/latex_delimiters.py -i <产出目录>/说明书.md
```
